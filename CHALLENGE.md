### CH-01. The ledger has no writer, so DELIVER does not unblock LEARN and Phase 8 is unfalsifiable

LENS:      strategic + creative + holistic (found independently by three of four lenses; merged)
CLAIM:     4.8 "Stage 9 LEARN cannot run without it. The ledger needs the skill to be in use. No installs means no runs, no ledger lines"; Phase 8 "Phase 6 is a hard dependency"; 4.10.1's table marking output correction as "Currently captured: yes, `ledger`".
WHY:       The step from installs to ledger lines is asserted, not built, and no phase builds it. In managed mode the ledger works because the operator's gate runs over the person's real work weekly and appends a line (`ctrl-check/SKILL.md:73-75`, verified). In self-serve, the equivalent gate runs once, at build time, on the package itself. After delivery the skill runs inside the person's own Claude and CTRL observes nothing: `mcp-context` is read-only by design (the mcp_tokens migration says exactly that, line 5), its only usage trace is one `last_used_at` timestamp overwritten per call, and the shipped generator already concedes the loop is manual (`prompt.ts:182`: "the leader brings those corrections back to CTRL"). So all three 4.10.1 signal classes are unwritable after Phase 6: output correction has no submission path, method correction has no surface, and trigger accuracy ("the skill was absent from the loaded set") happens in a session CTRL cannot see. Section 9's "mine the diff" forecloses the feedback-form patch, and there is no diff: CTRL never sees the second version. Phase 8's acceptance test seeds synthetic rows, so it passes in a world where zero real rows will ever arrive.
INSTEAD:   Three writers, named now, built in this order. (a) A paste-and-check review surface in CTRL (Phase 4): the person submits a real piece of work, gets the 4.6 output contract back, and their accept or push-back per verdict IS the ledger row. The review is the work and the row is the by-product, which is what "mine the diff" actually asks for; it reuses stages 5-7 unchanged, needs no plugin, works anonymous, and is the self-serve form of ctrl-check. (b) Per-call pull logging in `mcp-context` (Phase 6): one row per get_skill call (skill, tool, when) instead of a token timestamp. Honest and sufficient for Type C drift, which needs no verdict. (c) Optional: `record_review` / `record_trigger` write tools behind a new `write:ledger` scope (the scopes column exists), gated in `toolsFor`, with the package's required Learning-loop section carrying the instruction to call them; rows labelled self-reported. Then invert the dependency: Phase 8 depends on (a), not on Phase 6, and Phase 8's acceptance becomes one real ledger row from one real review, never seeded ones.
IF WRONG:  If leaders will not paste work back to be checked, the review surface gets no traffic and the ledger stays empty anyway, and the MCP write path was delayed for a screen nobody visits. Falsifiable in four weeks: under roughly one check per active user per week, the write tools stop being optional.
COST:      Phase 4 gains one screen plus one endpoint that already had to exist. Phase 6 gains a call-log insert and loses its status as the Phase 8 blocker, freeing the most expensive phase to be deferred. Phase 8's acceptance test becomes real.
DECISION:  accept the three writers and the dependency inversion, or restate 4.8 honestly (DELIVER unblocks USE, not LEARN) and accept that self-serve LEARN is manual paste-back.

### CH-02. The live-update claim does not survive `get_skill`, and the router-plus-leaves package cannot be served over MCP at all

LENS:      holistic
CLAIM:     4.8 "Over MCP the skill is pulled live, so when stage 9 sharpens a criterion the update lands without a reinstall. The difference between those two is the difference between a product and an export button."
WHY:       What is live is the fetch, not the content. `get_skill` returns `generated_artifacts.body`, a single text column written once at generation time (verified: `mcp-context/index.ts:107-116, 209-221`; migration `20260513000000`). Stage 9 appends deltas to `criteria` rows; nothing regenerates the artifact body, and no column records which criteria version the body was rendered from, so divergence cannot even be detected. Result: the standard moves, the installed skill does not, and both sides believe they are current, which is a gate drifting silently from its own artefact, the exact failure 5.5 says must never open. Second, harder: 4.4 restructures the package into a router plus `rubric/`, `exemplars/`, `references/`, `evals/`. `get_skill` returns one string. An 80-line router whose leaves cannot be fetched resolves to nothing on the far side, so the live-pull channel actively degrades the package relative to today's flat SKILL.md. Sections 4.4 and 4.8 were never checked against each other.
INSTEAD:   Two Phase 6 changes. (a) `criteria_version` and `rendered_at` in `generated_artifacts.metadata`; on proposal acceptance stage 9 marks affected artifacts stale; `get_skill` regenerates in the background (the existing waitUntil+poll pattern) or serves the current body with one honest line: compiled against version N, standard is now N+1. Never silently serve stale. (b) Decide the multi-file question before any marketplace ships: either `get_skill` gains a `file` argument plus `list_skill_files`, or it inlines the leaves beneath the router in one response.
IF WRONG:  If regeneration churns (a skill that changes between two runs of the same task is its own trust failure), the honest-staleness line is the fallback and the regeneration work is wasted. Falsifiable: fewer than one accepted criteria delta per user per quarter means live update was not worth building and the export-button framing was correct.
COST:      A metadata field, a staleness rule, one get_skill argument. Under a day, but it must be decided before Phase 6's headline claim is written into UX copy.
DECISION:  accept both (a) and (b), or drop the live-update claim from 4.8 and the delivery screen.

### CH-03. The discrimination test as specified is one global switch, has no machine to compute it, and the item-14 beat cannot honestly fire about half the time

LENS:      technical
CLAIM:     4.3 C's sufficiency row (`n_rejected < 4` or `n_accepted < 4` -> untested); 4.3 B's worked example ("7 of 9 rejected... 1 of 11 accepted", 9+11 = the whole training set); 6.1 "Item 14 is the earliest point a kill can be computed honestly".
WHY:       Five defects, all verified against the spec's own arithmetic. (1) `n_rejected`/`n_accepted` are counts over all 20 training items, identical for every criterion, so the sufficiency row is one global switch on the person's grade split: either every criterion is untested or none is. (2) Per 4.2, each of the 10 candidate constructs is targeted by exactly one pair, and holding out three whole pairs zeroes 3 of 10 candidates: they can never be tested at any threshold. (3) Nothing computes `n_rejected_failing`: no stage applies a candidate criterion to the 20 training items, and doing so is 100-160 zero-shot judgements with no exemplars and no rubric, the configuration 4.6 Rule 3 and section 9 forbid. `criteria` also has no `observable` column; the field the compiled rubric prints does not exist on the compiled table. (4) When the global switch trips (one skip or one rejected own item at the preamble-primed reject rates), zero criteria load, the Standard lens judges against an empty rubric, TP=FP=0, precision = 0/0 = NaN, and neither row of 4.7b's release table fires; item 30 renders NaN. (5) At item 14 the expected graded-training count is 9.3 and P(4-and-4 satisfied) is roughly 0.51 at a 50% reject rate, 0.27 at 70%: the beat 6.1 calls most important is unavailable about half the time, most often for exactly the discerning grader the product targets, and it fires between manipulation checks 1 and 2, so 4.3's halt precondition cannot be evaluated when the kill lands. (6.1 also cites the 4-and-4 rule as "(3.4)"; it lives in 4.3.)
INSTEAD:   Define n per criterion over items whose `targets` contain it, and state that it is 2 under the current composition. Re-budget the 20 synthesised items as 5 constructs x 2 pairs (same count, n=4 per construct, hold out one pair per construct, nothing zeroed). Add `observable` to `criteria` and compute the failing counts from a deterministic probe, not an LLM verdict; a construct that cannot yield a checkable probe is written untested with the reason. Take the first kill off a fixed item number: kills land when they compute, none before item 16, and 6.1's own fallback ("show nothing") becomes the design. Define the degenerate matrix: zero criteria loaded is `baseline: none`, never a computed number.
IF WRONG:  If the global split is the right unit, 5x2 halves construct coverage and the rubric compiles to 3-4 criteria, at the floor 4.4 sets for core.md. Falsifiable on the first Phase 2 run: log per-construct n and the global split beside the gap distribution and compare kill rates under each unit.
COST:      Phase 2 (item composition, beats), Phase 3 (probe pass, per-criterion counts), one column riding the Phase 1 migration batch. Roughly a day and a half total.
DECISION:  accept the per-criterion redefinition, the 5x2 re-budget, and the probe column, or defend the global switch.

### CH-04. Grade-vector clustering at 0.8 has no shared index set, so it either never merges or merges everything

LENS:      technical
CLAIM:     4.3 A: "Two constructs are the same criterion when the items targeting them were graded the same way, at >=0.8 agreement across the training items... Expect 8 to 15 in, 5 to 8 out."
WHY:       Agreement between two vectors needs a common index set and 4.2's composition provides none: constructs are targeted by disjoint pairs, so any two constructs share zero items. The three available implementations all fail: intersection-only agreement is 0/0 and nothing merges (silent no-op, 10 criteria, the 7-cap breached on the first run); projecting onto a 20-slot vector with nulls-as-agreement gives every pair 18/20 = 0.90 and everything merges; comparing the 2x2 grades directly admits only 1.0/0.5/0.0, so 0.8 means "identical" and two constructs merge whenever the pair design worked, not because the constructs are the same. The own and peer items carry empty `targets` and contribute nothing. The defect is not the `[U]` number; the quantity is undefined at this n, and "8 to 15 in, 5 to 8 out" cannot be produced by this mechanism under any threshold.
INSTEAD:   Cluster on the criterion-application vector: once each candidate criterion is scored against all 20 training items (which CH-03's probe pass produces anyway), each criterion has a length-20 fail/hold vector over the same items, and 0.8 becomes a stated significance level (at 20 shared observations, two independent 50%-fail criteria reach 16/20 agreement with p = 0.006). The person's grades stay as the label for the discrimination test, not the clustering feature. If the probe pass is declined, delete the clustering step and cap by weight and rank; a step that cannot compute its own statistic should not ship as one.
IF WRONG:  If application vectors are dominated by one axis, everything correlates and the clusterer over-merges. Detectable from the same Phase 2 log: emit the pairwise agreement matrix; median off-diagonal above ~0.7 means the vectors measure one thing and clustering switches off rather than retunes.
COST:      Phase 3 only; near-free if CH-03's probe pass is accepted, since it consumes the same matrix.
DECISION:  accept criterion-application clustering (with CH-03), or delete the clustering step.

### CH-05. Section 3's SQL leaves the load-bearing operation unguarded and makes two table classes unreachable

LENS:      technical
CLAIM:     (a) 3.2's `situation_required_when_situated` CHECK plus the gloss "A statement is context-bound until something proves it standing." (b) 3.4's `scope_matches_owner` CHECK against 3.0's criteria SELECT policy. (c) 3.0's orgs/org_members INSERT policies.
WHY:       (a) The CHECK is correct for `situated = true` and constrains nothing about `situated = false`. No stage is named as permitted to write it, no column records who promoted a statement to standing or on what evidence, and 4.1's deterministic post-check does not include "situated must be true on ingest". The single operation this document exists to prevent, situated becoming standing, is an unaudited one-column UPDATE; and since `prov.noSituatedGeneralisation` blocks from Phase 3 onward, the design is either unusable (nothing can ever become standing) or promoted through the hole. (b) A role-scoped criterion satisfies its CHECK with `user_id` NULL and `org_id` NULL, then matches neither branch of the SELECT policy: role criteria are invisible to everyone including their author, the identical bug class 3.0 says revision 1 had on the org row. (c) No org can ever be created: the orgs INSERT policy tests membership of an org that does not exist yet, and the first org_members row needs an owner row that cannot exist. `orgs.created_by` exists and the policy never uses it. Smaller, same family: `criteria` has no unique constraint (the 7-cap selects nondeterministically over possible duplicates), and 5.1's role_bundle subquery has LIMIT 1 with no ORDER BY.
INSTEAD:   Add `standing_promoted_by uuid`, `standing_at timestamptz`, `standing_evidence_ids uuid[]` and a CHECK mirroring `elicited_needs_evidence` (standing requires a promoter plus >=2 evidence ids); name the only writer: the person, through grade-sort, when two or more graded items separate on it; no LLM path writes it ever; add "every candidate is situated = true" to 4.1's deterministic post-check. Require org on role scope and add the third SELECT clause joining role_bundles to org_members. Bootstrap orgs via a SECURITY DEFINER function writing the org and the owner membership in one transaction, keyed on `created_by = auth.uid()`. Add `CREATE UNIQUE INDEX ON criteria (user_id, surface, name) WHERE is_current` and a deterministic tiebreak in 5.1.
IF WRONG:  The promotion threshold is the risk: if genuine promotions usually rest on one separating item, nothing ever becomes standing and every skill is a list of narrowly situated rules. Measurable in Phase 2 free: count constructs reaching two separating items per sort; median below two means the threshold is one, and the audit columns stand regardless.
COST:      Phase 1 (CREATE TABLE bodies, so it is now or a rewrite later), Phase 2 (the grade-sort promotion write), Phase 7 (RLS clauses). Half a day, the cheapest it will ever be.
DECISION:  accept the promotion audit columns and the three SQL fixes, or name a different promotion mechanism now.

### CH-06. The new tables sit outside CTRL's live compliance boundary, and three of them break account deletion outright

LENS:      holistic
CLAIM:     3.2 "`quote` is verbatim and immutable"; 3.1/3.7's `owner_user_id uuid NOT NULL REFERENCES auth.users` (and orgs.created_by) with no ON DELETE clause.
WHY:       Two live-facing mechanisms, both verified. (1) Retention: `evidence` becomes the richest personal-data store CTRL holds, and 4.1's primary input is call transcripts, so `quote` will hold other people's verbatim speech keyed to a user who is not the speaker. It has no retention column and is declared immutable, so no redaction path either. Meanwhile the live compliance page tells users "A retention window is in place" and GDPR Art 5(1)(e) is marked implemented on the strength of `cleanup-expired-data`, which touches only `user_memory` and `ai_cache` (verified). A 30-day-retention user gets the fact deleted from user_memory while the identical sentence survives forever in evidence. That is a faked green tick applied to a legal claim. (2) Erasure: `delete-account` sweeps a hardcoded 32-table list (verified at index.ts:163-173) that contains none of the eleven new tables, and `skill_provenance` has no user_id at all. Worse: the three `REFERENCES auth.users` columns above default to NO ACTION (the repo has 8 such references without ON DELETE already), so `auth.admin.deleteUser` raises an FK violation for any user owning a standard or proposal; the error lands in `deletionErrors` and the function still returns `success: true` (index.ts:284-291), and `AccountDeletionDialog` throws only on `data.error`, never reads `data.errors` (verified at :107-108), then shows done. The user is told erased; the identity survives. The one e2e test that would catch it is `test.describe.skip`.
INSTEAD:   Give `evidence` `retention_expires_at` plus the user_memory-style trigger, and extend the cleanup function to cover it. Add `speaker_is_owner boolean` (or `subject`) and a redaction path that empties `quote` while keeping the row, so third-party speech is removable without breaking shipped pointers (the provenance gate then sees a live row marked redacted, a truthful state). Put ON DELETE CASCADE on every new auth.users reference and add all eleven tables to sweepTables. Phase 0 gains: AccountDeletionDialog fails loudly on non-empty `data.errors`; unskip the e2e; fix the pre-existing `security_audit_log` FK. Re-verify whether Art 17 and Art 5(1)(e) can stay marked implemented, and downgrade them if not.
IF WRONG:  If evidence rows expire, shipped `[E]` pointers resolve to nothing and 7a deletes rules from artefacts already in use. That tension is real and is why redaction (keep row, empty quote) matters more than deletion. Falsifiable at Phase 5: run the provenance gate against a redacted-evidence package and check it degrades gracefully.
COST:      Phase 1 migration text (three FK clauses, one column, one trigger), three Phase 0 items, one call added to cleanup-expired-data. Under a day; it prevents shipping a schema that falsifies a live GDPR control on landing day.
DECISION:  accept all four moves, or explicitly accept the compliance exposure in writing.

### CH-08. Item 20 shows the person their compiled rubric, then measures the gate on grades made after it

LENS:      creative
CLAIM:     6.1 item 20 (rubric reveal, renaming invited) against 4.2 ("Position is randomised") and 4.7b (the number is computed from held-out grades).
WHY:       Held-out items are randomly positioned across all 30, so roughly a third are graded after the person has read their own compiled, weighted standard and endorsed it by renaming. Those grades are anchored; the gate is then scored against grades the rubric helped produce, inflating the one number the product calls earned. The document went to real trouble not to reveal WHICH items are the test (revision-2 defect 9), then shows the whole standard two-thirds through the session. Second: the preamble pre-normalises rejecting ("Most of these are deliberately mediocre"), so a discerning grader plausibly accepts fewer than 4 items among the first 14, which both starves the item-14 kill (see CH-03) and can leave every criterion untested at compile: a completed 30-item sort can return an empty rubric.
